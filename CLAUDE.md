# CinemaTracker — Codebase Guide

A single-page web app for tracking movies watched, ratings, lists, social feed,
data dashboards, AI recommendations, achievements, and custom themes. Vanilla
JS + HTML + CSS on the front end; **Supabase** (Postgres + Auth + Storage + Edge
Functions) on the back end. No build step, no framework, no bundler.

## 📌 KEEP THIS FILE CURRENT (do this every time)

**Whenever you add/remove/rename/move a file, feature, page, or notable function,
update this `CLAUDE.md` in the same change** so the file map, function list, and
script-load order below stay accurate. Treat updating this guide as part of the
task, not an optional extra. Specifically:
- New `assets/js/*.js` file → add it to the **File structure**, the **JS file map**
  table, and add its `<script src>` tag to `index.html` in the correct order.
- New/removed/renamed function → update the affected row in the JS file map.
- New page/route → note it under `02-router.js`.
- New back-end dependency (edge function / SQL / RPC) → update the **Back end**
  section.
After structural edits, you can regenerate the function inventory with:
`grep -rnE "^        (async function|function|class) " assets/js/`

## ⚠️ Critical constraints — read before editing JS

The front end was refactored from one giant `index.html` into many files, but it
is **NOT modular**. All the `assets/js/*.js` files are loaded as ordinary
(classic) `<script>` tags, in numeric order, at the end of `<body>` in
`index.html`. They all share **one single global scope**. This has hard rules:

1. **Load order matters.** The `<script src=...>` tags in `index.html` are
   ordered `01` → `18`, then `20-leaderboard.js`, `21-swipe-deck.js`,
   `22-account-fun.js`, `23-movie-spotlight.js`, `24-notifications.js`,
   `25-games.js`, then `19-logging-boot.js`.
   `01-config.js` defines globals (`supabaseClient`, `icons`, `COL_WATCH_DATE`)
   that everything else depends on; `19-logging-boot.js` runs the boot sequence
   (`DOMContentLoaded`, etc.) and **must stay last** — so the higher-numbered
   `20-leaderboard.js` / `21-swipe-deck.js` / `22-account-fun.js` are intentionally
   loaded just *before* it.
2. **No `import`/`export`, no `type="module"`.** Adding modules would break the
   shared-scope model and every inline `onclick="..."` handler.
3. **Functions are global by design.** The HTML markup in `index.html` calls them
   inline (e.g. `onclick="router.navigate('home')"`, `onclick="openAuthModal()"`).
   A function defined in any file is callable from any other file and from inline
   handlers. Do not wrap files in IIFEs or change a top-level `function`/`const`
   to something scoped.
4. **A function can live in a different file than where it's used.** Files were
   split by original source order, not perfectly by domain. If you can't find a
   function, grep all of `assets/js/`:
   `grep -rn "functionName" assets/js/`
5. **Don't assume a file is self-contained.** Cross-file calls are everywhere
   (e.g. dashboard code calls theme/auth helpers).

If you ever need to recombine or re-split, the untouched pre-refactor originals
are in `_original_backup/` (`index.html.bak`, `reset-password.html.bak`).

## Back end (reference, in repo root)

These are deployed to Supabase, not loaded by the front end, but document the API
the front end calls:
- Edge Functions: `EdgeFunc` (deployed as `swift-api`), `edgefunccopy`,
  `color_theme_edge.js`, `taste_profile_edge.js` (deployed as **`swift-responder`**;
  the front end calls these via
  `callSwiftApi*` / `callColorThemeEdge` in `12-watch-modals.js` and
  `08-search-trending.js`). **`taste_profile_edge.js` computes & upserts the
  `Taste Profiles` row** (core compute is the reusable `computeAndStoreTasteProfile(supabaseAdmin, userId)`): mean/median/std overall, like_threshold (75th pct),
  imdb_delta, subrating correlation weights, runtime/decade bins, **per-person and
  per-genre affinity** — every group average is **Bayesian-shrunk toward the user's
  mean** (`SHRINK_K=5`) so sparse groups don't read as strong signal; people require
  ≥2 rated movies. Also computes **swipe-appeal** (`swipe_genre_affinity_json`): a
  WEAK per-genre right-swipe-rate **lift** from the Discover deck's `swipes`, kept
  separate from the ratings-based affinity. Also generates the cached **AI taste
  blurb** (`Taste Profiles.taste_blurb`) — a Claude call (`ANTHROPIC_API_KEY`,
  model `ANTHROPIC_MODEL_BLURB`, default `claude-haiku-4-5-20251001`) that turns the
  computed signals into a one-line taste snippet for the fun Account page; it's
  best-effort (omitted from the upsert on failure so the prior value persists, and
  skipped under ~3 ratings). **Two ways it stays fresh, no longer tied to opening AI Picks:**
  (1) **event-driven** — `recomputeMyTasteProfile()` (in `12-watch-modals.js`) is fired
  fire-and-forget after every rating save/edit in `handleFormSubmit` (`10-logging-form.js`)
  and still right before an AI Picks run (`16-ai-picks.js`); it POSTs `{user_id}` with the
  caller's bearer so the function rebuilds just that user (auth check: a caller can only
  recompute themselves). (2) **cron/batch** — a `CRON_SECRET`-gated mode (send the
  `x-cron-secret` header, no user session): `{limit, concurrency}` recomputes the
  **stalest-profile-first** batch of all raters (`fetchTasteRecomputeTargets`; `limit:0`
  = everyone, which is also the one-time backfill), driven by
  `.github/workflows/refresh-taste-profiles.yml` (daily 08:30 UTC; repo secrets
  `SUPABASE_TASTE_FUNCTION_URL` = the `…/functions/v1/swift-responder` URL +
  `SUPABASE_PUBLISHABLE_KEY` + `CRON_SECRET`, and the edge secret `CRON_SECRET`).
  `EdgeFunc` dispatches by `body.action`; notable actions
  include `search`, AI picks (the `ai_picks` action **reads that Taste Profile and
  scores every candidate with `predictTasteScore(model, features)`** — a reusable
  0-100 prediction from genre+decade affinity (+ keyword/theme affinity when a movie's
  keywords are known — inert for AI Picks discover candidates, ready for the per-movie/swipe
  predictor) + a crowd/imdb_delta anchor + a WEAK swipe-appeal genre nudge
  (`swipe_genre_affinity_json`, Phase 3), with short
  `taste_reasons`; candidates are sorted by it, the rerank LLM is told to treat it as
  a primary ranking factor (not a tie-breaker) and weave the reasons into its
  explanations, **but the PROMPT outranks taste** (mood-dependent — an explicit
  against-taste request follows the prompt), and `taste_score` is returned on each pick. No-genre "surprise me"
  prompts also lean toward the user's top-affinity genres), `swipe_deck` (powers the
  Discover swipe deck in `21-swipe-deck.js` — returns a ranked batch of unseen movie
  cards, scored by `predictTasteScore` with a little random jitter for variety, excluding
  movies already rated/logged, right-swiped ever, left-swiped in the last 30 days via the
  `swipes` table, or already on the caller's **Bucket List or Recs** list (resolved
  `Movie Lists`→`Movies.tmdb_id`); no LLM.
  **⚠️ CANDIDATES COME FROM THE SHARED `Rec Pool` TABLE — NOT a live TMDB crawl. Do not
  reintroduce per-user TMDB calls on this path.** This was redesigned: candidate generation
  used to crawl TMDB `/discover` **per user, at request time** (6 sequential TMDB calls per
  batch, up to 5-6 batches deep). But the candidate set is essentially the SAME for
  everybody — only the SCORING and the EXCLUSIONS are personal — so we were paying a
  per-user crawl for a shared result: the nightly `build_home_recs` cron fired ~36 TMDB
  calls × 150 users in ONE edge invocation (it timed out), and any user it missed fell
  through to a slow, failure-prone live crawl on every Home visit (which is what made the
  "You Might Like" strip vanish). Now **one cron crawls TMDB once a day for everyone**
  (`build_rec_pool`) and a user's deck is a pure DB read + in-memory scoring with **zero
  external API calls on the read path** (a handful of indexed queries, well under a second).
  The core compute is the reusable module-level
  **`computeSwipeDeck(supabaseAdmin, supabaseUserClient, uid, {limit, batch, tmdbToken, includeTrending, shared})`**
  helper — the live `swipe_deck` + `home_recs` actions call it with the caller's clients;
  the `build_home_recs` cron calls it per-user with `supabaseUserClient=null` (which just
  skips the follows source — its rpc is already try/caught). `tmdbToken` is still accepted
  for signature compatibility but is **no longer used**. **`batch`** now pages through the
  RANKED pool (batch N = the Nth slice of `limit` cards; an out-of-range batch returns `[]`,
  which the client reads as "pool exhausted") instead of paging TMDB deeper.
  **`includeTrending`** (default true) no longer pulls a separate trending source — the pool
  already carries recent films — it now just **tilts the ranking toward currently-hot titles**
  (recent + high `popularity`); Discover keeps it (sends nothing → default true), the home
  strip opts OUT (`build_home_recs` / `home_recs` pass `includeTrending:false`).
  **`shared`** lets a caller looping over MANY users (the `build_home_recs` cron) do the
  user-INDEPENDENT reads — the pool (`fetchRecPool`), the catalog IMDb vote counts
  (`fetchCatalogVotesByTmdb`), the Settings threshold (`fetchReviewThreshold`) — **once per
  run** instead of per user.
  **`build_rec_pool`** (**cron**, `x-cron-secret`==`CRON_SECRET`, no user session) is what
  fills the pool: it crawls TMDB `/discover` into the **`Rec Pool`** table (`rec_pool.sql`),
  deliberately broad so everyone doesn't see the same 60 blockbusters — all-time most-voted
  (the canon) + **per GENRE** most-voted + **per DECADE** most-voted + recent/popular. Every
  column stored comes FREE in the `/discover` response (**no OMDb, no per-movie TMDB
  lookup**), so a ~3-5k movie pool costs only **~150 TMDB calls per run, TOTAL, for all
  users** — and it doesn't touch the OMDb quota. Upserts on `tmdb_id`, so re-runs just
  refresh. Driven by `.github/workflows/build-rec-pool.yml` (daily, 30 min BEFORE
  refresh-home-recs so decks are built off a fresh pool).
  **`home_recs`** (**authenticated**) serves the Home strip's **STABLE DAILY DECK**: if the
  caller's `Home Recommendations` row was computed TODAY (Pacific, `gamePuzzleDatePT`) it
  returns it unchanged; otherwise it computes the deck via `computeSwipeDeck` and **SAVES**
  it, so the picks stay stable for the rest of the day. This is what a brand-new account (or
  a user the cron hasn't reached) hits — one cheap call, no TMDB — replacing the old
  deep-paged live `swipe_deck` fallback. `build_home_recs` (**cron**) precomputes the same
  rows for everyone nightly (stalest-`computed_at` first, `limit`/`concurrency`/`deck_size`
  body params; returns **409** if the `Rec Pool` is empty) — driven by
  `.github/workflows/refresh-home-recs.yml`.
  **Redeploy `swift-api` after the Rec Pool refactor**, and run `rec_pool.sql` + the
  `build-rec-pool.yml` workflow once first (an empty pool = an empty deck).

## ⚠️ Database schema — where every field actually lives

**Source of truth: the CSV exports in `Supabase Setup/` (one file per table; the
header row = that table's columns).** Read the relevant CSV header before writing
any query. Do NOT guess column locations.

**The #1 trap: movie metadata is split across tables. `Movies` holds only core
fields. Genre, director/cast, keywords, platforms, and external (IMDb) ratings each
live in their own join tables — they are NOT columns on `Movies`.** Selecting a
non-existent column makes the whole PostgREST query fail and return nothing.

### How to read denormalized movie data
The front end usually reads **genre/director/platforms together via SQL views**
(`library_views.sql` → `user_library_items_v2`, `user_movie_latest_watch`), not by
joining the base tables itself. Server-side (Edge Function) you must join the base
tables manually: genre = `Movie Genres`→`Genres`; director = `Movie Crew`
(`job='Director'`)→`People`.

## Editing conventions

- Match the existing style: top-level code in each file is indented **8 spaces**
  (carried over from when it was nested inside `<script>` in `index.html`). Keep
  new code consistent with the surrounding lines rather than re-indenting.
- Inline `onclick`/`oninput` handlers in `index.html` markup require their target
  functions to remain global — don't rename a function without updating its
  callers in `02-router.js` templates and `index.html`.
- When adding a new feature file, give it the next number, add its `<script src>`
